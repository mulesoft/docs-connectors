= RosettaNet Connector Listener Mode - Shared - Example

This example uses two Mule applications. Three Buyers send purchase orders to one Seller. The Seller receives those purchase orders through one RosettaNet configuration in `SHARED` listener mode.

* `demo-multiple-buyers` hosts Buyer A, Buyer B, and Buyer C.
* `demo-shared-mode-seller` hosts the shared Seller hub.

The shared configuration is inbound-only. Every *Send action* in this example uses a `DEDICATED` listener mode configuration.

[[configure-external-libraries]]
== Configure a Global Element for External Libraries

Mule applications using RosettaNet Connector must contain only one global element configuration to provide the external libraries required for the selected security mode.

To configure the global element for RosettaNet Connector and add external libraries, follow these steps:

. In Anypoint Studio, open the Mule project.
. Click *Global Elements*, then click *Create*.
. Search for and select *RosettaNet External Libs - Non FIPS*.
. Click *Configure* > *Add recommended libraries*.
. Click *OK* to add the required dependencies and shared libraries to the application `pom.xml` file.

For other security modes, see xref:rosettanet-connector::rosettanet-connector-upgrade-migrate.adoc#configure-external-libraries[Configure External Libraries].

== Buyer Application

Each Buyer uses `DEDICATED` listener mode configurations. One sends the Purchase Order request and receives its receipt acknowledgment. A second receives the Purchase Order Confirmation and automatically returns its receipt acknowledgment to the Seller.

The Buyer application performs the following actions:

. Receives a purchase order document through one of the Buyer API endpoints.
. Uses a dedicated initiator configuration to send the Purchase Order request to the Seller shared listener.
. Receives the receipt acknowledgment for the outbound purchase order and reports its completion through the matching *Completion source*.
. Receives the Purchase Order Confirmation through a dedicated initiator configuration and *Action source*.
. Automatically sends the Purchase Order Confirmation receipt acknowledgment to the Seller's matching dedicated confirmation configuration.

NOTE: The demonstration certificate aliases use the location identifiers `partnera`, `partnerb`, and `partnerc`. These are protocol identifiers only; the applications, flows, and endpoints refer to Buyer A, Buyer B, and Buyer C.

== Seller Application

The Seller receives all purchase orders through a single shared responder configuration. It stores the reply attributes separately for each Buyer, then sends each confirmation through a dedicated responder configuration.

The Seller application performs the following actions:

. Receives Purchase Order requests from Buyer A, Buyer B, and Buyer C through one shared responder *Action source*.
. Identifies the sending Buyer from the business identifier, location identifier, and certificate alias in the incoming delivery header.
. Sends the receipt acknowledgment or exception signal to the matching Buyer by using that Buyer's shared-listener partner entry.
. Stores the reply attributes for each received Purchase Order under a Buyer-specific Object Store key.
. Uses a dedicated responder configuration to send each Purchase Order Confirmation to its Buyer.
. Receives the receipt acknowledgment or exception signal for each confirmation through the matching dedicated *Completion source*.

=== Create the Seller Flows

. Add one *Action source* flow using `seller-buyers-shared-responder-config`. Store `attributes.replyAttributes.messageId`, `actionId`, and `pipInstanceId` under a Buyer-specific Object Store key.
. Add one HTTP Listener and *Send action* flow for each Buyer. Retrieve the matching Object Store value and set the *Reply to* values on *Send action*.
. Add one *Completion source* flow for each dedicated Seller confirmation configuration.

The Seller endpoints are:

* `POST /api/buyers/a/purchase-order-confirmations`
* `POST /api/buyers/b/purchase-order-confirmations`
* `POST /api/buyers/c/purchase-order-confirmations`
* `GET /api/status`

== Test the Examples

Start `demo-multiple-buyers` and `demo-shared-mode-seller` before testing. The Buyer API listens on port `8083` and the Seller API listens on port `8080`. Download a https://s3-us-west-2.amazonaws.com/mulesoft-sites-vendorcontent/public-assets/sample-purchase-order-request-content.xml[sample purchase order request] and a https://s3-us-west-2.amazonaws.com/mulesoft-sites-vendorcontent/public-assets/sample-purchase-order-confirmation-content.xml[sample purchase order confirmation], or use equivalent documents for the configured PIP.

=== Send a Purchase Order

. Send a purchase order from each Buyer to the Seller `SHARED` listener mode:
+
[source,bash,linenums]
----
curl -v -H "Content-Type: application/xml" -X POST --data-binary @sample-purchase-order-request-content.xml http://localhost:8083/api/buyers/a/purchase-orders
curl -v -H "Content-Type: application/xml" -X POST --data-binary @sample-purchase-order-request-content.xml http://localhost:8083/api/buyers/b/purchase-orders
curl -v -H "Content-Type: application/xml" -X POST --data-binary @sample-purchase-order-request-content.xml http://localhost:8083/api/buyers/c/purchase-orders
----

The Seller receives each request through the shared *Action source*. Verify that the logs show the matching Buyer name and message ID, followed by the Buyer's completion message. For example:
+
[source,java,linenums]
----
INFO  ... Seller received purchase order <message-id> from Buyer-A
INFO  ... Buyer A purchase order <message-id> completed as SUCCESS
----

=== Send a Purchase Order Confirmation

. After a Buyer sends a purchase order, send the correlated Purchase Order Confirmation to that Buyer:
+
[source,bash,linenums]
----
curl -v -H "Content-Type: application/xml" -X POST --data-binary @sample-purchase-order-confirmation-content.xml http://localhost:8080/api/buyers/a/purchase-order-confirmations
curl -v -H "Content-Type: application/xml" -X POST --data-binary @sample-purchase-order-confirmation-content.xml http://localhost:8080/api/buyers/b/purchase-order-confirmations
curl -v -H "Content-Type: application/xml" -X POST --data-binary @sample-purchase-order-confirmation-content.xml http://localhost:8080/api/buyers/c/purchase-order-confirmations
----

Verify that each Buyer receives its confirmation and that the Seller completion flow logs the message ID and completion code. For example:
+
[source,java,linenums]
----
INFO  ... Buyer A received purchase order confirmation <message-id> from Seller
INFO  ... Seller confirmation <message-id> to Buyer A completed as SUCCESS
----

IMPORTANT: Send a purchase order before sending that Buyer's confirmation. The Seller confirmation flow needs the correlated reply attributes stored by the shared purchase-order action flow.

== Shared Listener Mode Constraints

* Use a `SHARED` listener mode configuration for inbound fan-in from multiple partner identities.
* Do not use *Send action* on a `SHARED` listener mode configuration. Use a `DEDICATED` listener mode configuration for every outbound action.
* The configuration that sends an outbound message must receive its acknowledgment or exception signal because it owns the pending-message state used by *Completion source*.
* A `SHARED` listener mode selects a partner from the incoming delivery header and validates the configured business identifier, location identifier, and certificate alias.
