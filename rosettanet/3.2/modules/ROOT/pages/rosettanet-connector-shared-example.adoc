= RosettaNet Connector Listener mode - Shared - Example

This example extends the Buyer app in the dedicated listener mode example to communicate with multiple partners. The Buyer app sends purchase order requests to Seller A, Seller B, and Seller C, each using a separate initiator configuration. The Buyer app also receives RosettaNet action messages from the sellers through one shared listener configuration. The *Action source* uses the partner identifiers in each incoming message to select the matching partner entry and send acknowledgment and exception signals to that seller.

The following section provides instructions for configuring the global element for external libraries. Configure it once in each application.

[[configure-external-libraries]]
== Configure a Global Element for External Libraries

Mule applications using RosettaNet Connector must contain only one global element configuration to provide the external libraries required for the selected security mode.

To configure the global element for RosettaNet Connector and add external libraries, follow these steps:

. In *Package Explorer* or Anypoint Studio canvas, open your Mule flow or configuration.
. Click *Global Elements*. Or click *Create global element*, and then click the plus icon next to Global Elements.
. Click *Create*, and then search for the `RosettaNet` or `External Libs` option and select *RosettaNet External Libs - Non FIPS*.
. Name the configuration.
. Click *Configure* > *Add recommended libraries*.
. Click *OK* to include the libraries as dependencies and shared libraries in the Mule application `pom.xml` file.
. Verify that your project has the required dependencies for your security mode. Add the dependencies via Maven if they aren't added automatically.

For configuration instructions for other security modes, see xref:rosettanet-connector::rosettanet-connector-upgrade-migrate.adoc#configure-external-libraries[Configure External Libraries].

== Buyer App

The Buyer app performs the following actions:

. Sends purchase order requests to Partner A, Partner B, and Partner C, each through a separate *Send action* flow using a dedicated initiator configuration.
. Receives RosettaNet action messages from the partners through one shared *Action source*.
. Identifies the sending partner from the business identifier and location identifier in the incoming message.
. Receives completion events for inbound messages and for purchase order requests sent to each partner.

NOTE: Add the following JKS files to the Buyer app under `src/main/resources/crypto`: `hub.jks` for RosettaNet message signing, `hub-https.jks` for the HTTPS listener, and `partners-https-truststore.jks` to trust the HTTPS certificates presented by Seller A, Seller B, and Seller C.

=== Create the First Flow of the Buyer App

The first flow of the Buyer app sends a purchase order request to each partner. Create a dedicated initiator configuration and a *Send action* flow for each partner. First, configure an HTTP request global element for each partner.

==== Add the Partner Initiator Global Elements

The Buyer app sends a purchase order request to each partner using a separate *Send action* flow. Configure a dedicated initiator global element for each partner. The `Buyer_To_Partner_Initiator_Config` name identifies the Buyer app's initiator configuration and the partner it sends to. For example, `Buyer_To_PartnerA_Initiator_Config` sends to Partner A.

In each *RosettaNet Config* window, use the corresponding partner values:

[%header%autowidth.spread]
|===
|Field|Partner A|Partner B|Partner C
|Name|Buyer_To_PartnerA_Initiator_Config|Buyer_To_PartnerB_Initiator_Config|Buyer_To_PartnerC_Initiator_Config
|Global HTTP Listener|Buyer_Listener|Buyer_Listener|Buyer_Listener
|Service Endpoint Path|/rosettanet/hub-signal-a|/rosettanet/hub-signal-b|/rosettanet/hub-signal-c
|Global HTTP Request|Buyer_To_PartnerA_Request|Buyer_To_PartnerB_Request|Buyer_To_PartnerC_Request
|Request Endpoint Path|/rosettanet/partnera|/rosettanet/partnerb|/rosettanet/partnerc
|Keystore Path|crypto/hub.jks|crypto/hub.jks|crypto/hub.jks
|Keystore Access password|nosecret|nosecret|nosecret
|Signing key password|nosecret|nosecret|nosecret
|Global usage code|Production|Production|Production
|Mule DUNS identifier|999999999|999999999|999999999
|Mule location identifier|hub|hub|hub
|Partner DUNS identifier|111111111|222222222|333333333
|Partner location identifier|partnera|partnerb|partnerc
|Role in PIP|INITIATOR|INITIATOR|INITIATOR
|PIP definition path|/PIP3A4/V02_02.xml|/PIP3A4/V02_02.xml|/PIP3A4/V02_02.xml
|Listener mode|DEDICATED|DEDICATED|DEDICATED
|Signing override|NEVER|NEVER|NEVER
|===

==== Add the Send Action Operations

Create one flow for each partner. In each flow, add the *Send action* operation and select the matching initiator configuration in *Module configuration*. Add a *Transform Message* component or other components needed to prepare the purchase order request.

The three flows have the same structure. Only the *Module configuration* changes: select `Buyer_To_PartnerA_Initiator_Config`, `Buyer_To_PartnerB_Initiator_Config`, or `Buyer_To_PartnerC_Initiator_Config` to send the purchase order request to the corresponding partner. Shared listener mode applies to the Buyer app's inbound *Action source*; each outbound destination uses its own dedicated configuration.

==== Add the HTTP Request Global Elements

Create an HTTP request configuration for each partner. In the *HTTP Request configuration* window, configure the following values:

[%header%autowidth.spread]
|===
|Field|Partner A|Partner B|Partner C
|Name|Buyer_To_PartnerA_Request|Buyer_To_PartnerB_Request|Buyer_To_PartnerC_Request
|Host|localhost|localhost|localhost
|Port|8490|8491|8492
|Protocol|HTTPS|HTTPS|HTTPS
|Trust store path|crypto/partners-https-truststore.jks|crypto/partners-https-truststore.jks|crypto/partners-https-truststore.jks
|Trust store password|nosecret|nosecret|nosecret
|===

Use the partner's HTTP request configuration in its RosettaNet initiator configuration. The trust store contains the certificates for the partner HTTPS endpoints.

==== Add the Shared Responder Global Element

Add a RosettaNet configuration for the shared *Action source*. In the *RosettaNet Config* window, complete the following fields:

[%header%autowidth.spread]
|===
|Field|Value
|Name|Buyer_Hub_Shared_Responder_Config
|Global HTTP Listener|Buyer_Listener
|Service Endpoint Path|/rosettanet/hub-receive
|Keystore Path|crypto/hub.jks
|Keystore Access password|nosecret
|Signing key password|nosecret
|Global usage code|Production
|Mule DUNS identifier|999999999
|Mule location identifier|hub
|Role in PIP|RESPONDER
|PIP definition path|/PIP3A4/V02_02.xml
|Listener mode|SHARED
|Signing override|NEVER
|===

Add a partner entry for each partner. Each entry maps the partner's business and location identifiers to the HTTP request configuration and path used to send acknowledgment and exception signals to that partner:

[%header%autowidth.spread]
|===
|Partner name|Partner DUNS identifier|Partner location identifier|Global HTTP Request|Request Endpoint Path
|Partner-A|111111111|partnera|Buyer_To_PartnerA_Request|/rosettanet/partnera
|Partner-B|222222222|partnerb|Buyer_To_PartnerB_Request|/rosettanet/partnerb
|Partner-C|333333333|partnerc|Buyer_To_PartnerC_Request|/rosettanet/partnerc
|===

Shared listener mode uses the partner identifiers in the incoming message to select the matching partner entry. Add a partner entry for each partner that sends messages to the Buyer app.

=== Create the a flow to Receive Action Messages in the Buyer App

Add a flow to the Buyer app to receives action messages from the partners. Configure one shared responder global element for all partners, then use it in the *Action source*.


==== Configure the Action Source

Configure the *Action source* source to receive messages from all partners:

. From the *Mule Palette* view, select *RosettaNet* and drag the *Action source* source to the canvas.
. In the *Module configuration* field, select the shared responder configuration.
. Add a *Logger* component next to *Action source* to log the partner name and message ID. In the *Message* field, enter:
+
`Buyer received action message #[attributes.messageId] from #[attributes.partnerName]`

=== Create the Completion Flows of the Buyer App for each Partner

Add a separate flow for each partner that the Buyer app receives completion events for messages sent to sellers.
Add a *Completion source* for each dedicated initiator configuration to observe acknowledgment or exception signals for messages sent to that seller.

==== Add a Logger Component

Add a *Logger* component next to each *Completion source* to log the message ID and completion code. In the *Message* field, enter the following text in each flow:
+
`Buyer action message #[attributes.replyAttributes.messageId] completed as #[payload.completionCode]`

Select `Buyer_To_PartnerA_Initiator_Config`, `Buyer_To_PartnerB_Initiator_Config`, or `Buyer_To_PartnerC_Initiator_Config` as the *Module configuration* for the matching completion flow.

==== Save and Run the App

To save the app, click *File > Save*.

To run the app, click *Run > Run as > Mule Application*.

== Seller Apps

The Seller app performs the following actions:

. Sends purchase order acknowledgments to buyer, through a separate *Send action* flow using a dedicated Initiator configuration.
. Receives RosettaNet action messages from the buyer through one dedicated Responder configuration used for *Action source*.
. Receives completion events for inbound messages and for purchase order acknowledgments sent to the buyer.

NOTE: Add the JKS files for each seller to that app under `src/main/resources/crypto`. Seller A uses `partner-a.jks` for RosettaNet message signing and `partner-a-https.jks` for its HTTPS listener. Seller B uses `partner-b.jks` and `partner-b-https.jks`; Seller C uses `partner-c.jks` and `partner-c-https.jks`. Each seller also needs `hub-https-truststore.jks` to trust the Buyer app's HTTPS certificate.

The Partner A, Partner B, and Partner C can be hosted as seperate Seller apps each receive messages from the Buyer app and can send messages to the Buyer app. To simplify the example, the three Seller apps are combined into one app with three dedicated listener and initiator configurations. Configure each partner with its own identifiers, endpoint paths, and signing keystore. Set the partner DUNS identifier and location identifier in each seller configuration to the Buyer's values (`999999999` and `hub`).

NOTE: This example can be split up as separate apps, each with its own dedicated listener and initiator configuration in which case they will have the same structure; only the identifiers, endpoint paths, and signing keystore values differ by seller and they may need to run at same time.

==== Configure the Action Source

Configure the *Action source* source to receive messages from the Buyer app:

. From the *Mule Palette* view, select *RosettaNet* and drag the *Action source* source to the canvas.
. In the *Module configuration* field, select the seller's responder configuration.
. Add a *Logger* component next to *Action source* to log the received message ID. In the *Message* field, enter the corresponding value:
+
* Seller A: `Seller A received action message #[attributes.messageId]`
* Seller B: `Seller B received action message #[attributes.messageId]`
* Seller C: `Seller C received action message #[attributes.messageId]`

=== Create the Third Flow of Each Seller App

== Test the Examples

Run the Buyer app and all Seller apps. The Buyer app listens for test requests on port `8080`; the Seller apps listen on port `8083`. Download a https://s3-us-west-2.amazonaws.com/mulesoft-sites-vendorcontent/public-assets/sample-purchase-order-request-content.xml[sample purchase order request] and https://s3-us-west-2.amazonaws.com/mulesoft-sites-vendorcontent/public-assets/sample-purchase-order-confirmation-content.xml[sample purchase order confirmation], or use equivalent documents for the configured PIP.

=== Send Purchase Order Requests from the Buyer App

Post a purchase order request to each Buyer app endpoint. Each endpoint selects the dedicated initiator configuration for its Seller app:

[source,bash,linenums]
----
curl -v -H "Content-Type: application/xml" -X POST --data-binary @sample-purchase-order-request-content.xml http://localhost:8080/api/send-to-partner-a
curl -v -H "Content-Type: application/xml" -X POST --data-binary @sample-purchase-order-request-content.xml http://localhost:8080/api/send-to-partner-b
curl -v -H "Content-Type: application/xml" -X POST --data-binary @sample-purchase-order-request-content.xml http://localhost:8080/api/send-to-partner-c
----

The Seller apps receive the requests through their dedicated *Action source* flows. Verify that the logs show the matching seller and message ID, followed by the Buyer app's completion message, for example:

[source,java,linenums]
----
INFO  ... Seller A received action message <message-id>
INFO  ... Buyer action <message-id> completed as SUCCESS
----

=== Send Action Messages from the Seller Apps

Post a purchase order confirmation to each Seller app endpoint to send an action message to the Buyer app's shared *Action source*:

[source,bash,linenums]
----
curl -v -H "Content-Type: application/xml" -X POST --data-binary @sample-purchase-order-confirmation-content.xml http://localhost:8083/api/partner-a/send-to-hub
curl -v -H "Content-Type: application/xml" -X POST --data-binary @sample-purchase-order-confirmation-content.xml http://localhost:8083/api/partner-b/send-to-hub
curl -v -H "Content-Type: application/xml" -X POST --data-binary @sample-purchase-order-confirmation-content.xml http://localhost:8083/api/partner-c/send-to-hub
----

Verify that the Buyer app's shared *Action source* logs the message ID and the matching partner name (`Partner-A`, `Partner-B`, or `Partner-C`). The Seller app's completion flow should also log the message ID and completion code, for example:

[source,java,linenums]
----
INFO  ... Buyer received action message <message-id> from Partner-A
INFO  ... Seller A action <message-id> completed as SUCCESS
----

The sample purchase order confirmation is for demonstration. For a real purchase order confirmation, configure the `replyAttributes` on the RosettaNet *Send action* operation with the information from the corresponding purchase order request.
