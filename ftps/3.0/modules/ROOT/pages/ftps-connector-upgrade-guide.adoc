= Upgrading and Migrating FTPS Connector to Version 3.0

Upgrade Anypoint Connector for FTPS (FTPS Connector) to version 3.x.

== Supported Upgrade Paths

[%header,cols="50a,50a"]
|===
|From Version | To Version
|2.x |3.0.x
|===

== Changes in This Release

This release contains the following changes.

=== Runtime and Java Requirements

* FTPS Connector 3.0 requires Mule 4.9.0 or later and Java 17. Apps that run on Mule 4.8 or earlier, or on Java 8 or 11, must stay on FTPS Connector 2.x.

=== Standalone Connector

* FTPS Connector is now a standalone connector. It runs on a shared FTP engine library that FTP Connector 3.0 also uses, and it no longer includes FTP Connector.
* If the app uses `ftp:*` operations or configurations and depends only on FTPS Connector, add FTP Connector to the app explicitly. Otherwise, the app fails to deploy with an unknown namespace error.
* An FTP configuration that uses an FTPS connection (`ftps:connection` inside `ftp:config`) is no longer supported and fails to deploy. Use `ftps:config` instead.

=== Package Changes

* The connector packages moved from `com.mulesoft.extension.ftps.*` to `com.mulesoft.connectors.ftps.*`. Only `com.mulesoft.connectors.ftps.api.ftp`, `com.mulesoft.connectors.ftps.api.matchers`, `com.mulesoft.connectors.ftps.api.mode`, and `com.mulesoft.connectors.ftps.api.proxy` are exported. Custom Java code that references the 2.x classes, or `org.mule.extension.ftp.*` classes through FTPS Connector, fails to compile or load. Update it to use the new packages.

[[renamed-parameters]]
=== Renamed Parameters

The time unit parameters are renamed. The old names are no longer accepted, and an app that uses them fails to deploy with an XML validation error. In Anypoint Studio, the old names are flagged after you update the connector version.

[%header%autowidth.spread]
|===
|2.x Parameter |3.0 Parameter |Used In
|*Connection Timeout Unit* (`connectionTimeoutUnit`) |*Connection Timeout Time Unit* (`connectionTimeoutTimeUnit`) |`ftps:connection`
|*Response Timeout Unit* (`responseTimeoutUnit`) |*Response Timeout Time Unit* (`responseTimeoutTimeUnit`) |`ftps:connection`
|*Time Between Size Check Unit* (`timeBetweenSizeCheckUnit`) |*Time Between Size Check Time Unit* (`timeBetweenSizeCheckTimeUnit`) |`ftps:config`, `ftps:read`, `ftps:listener`
|*Time Unit* (`timeUnit`) |*Not Updated In The Last Time Unit* (`notUpdatedInTheLastTimeUnit`) and *Updated In The Last Time Unit* (`updatedInTheLastTimeUnit`) |`ftps:matcher`
|===

*Time Unit* (`timeUnit`) on `ftps:matcher` is replaced by two fields. *Not Updated In The Last Time Unit* (`notUpdatedInTheLastTimeUnit`) qualifies *Not Updated In The Last*, and *Updated In The Last Time Unit* (`updatedInTheLastTimeUnit`) qualifies *Updated In The Last*. Both default to `SECONDS`, which is the same default *Time Unit* had in 2.x. An app that still sets `timeUnit` fails XML validation.

[[changed-defaults]]
=== Changed Default Values

* The default value of *Time Between Size Check Time Unit* (`timeBetweenSizeCheckTimeUnit`) in the connector configuration is now `SECONDS`. In 2.x, the default was `MILLISECONDS`. For example, `timeBetweenSizeCheck="2"` without a unit now waits 2 seconds instead of 2 milliseconds. To keep the 2.x timing, set `timeBetweenSizeCheckTimeUnit="MILLISECONDS"`.
* The *Read* operation and the *On New or Updated File* source use the configuration values of *Time Between Size Check* and *Time Between Size Check Time Unit* unless you set them on the operation or source.
* In *Ftps explicit mode*, *PROT Settings* (`protSetting`) now defaults to `PRIVATE`. The connector sends `PBSZ 0` and `PROT P` after login and encrypts the data channel. In 2.x, when *PROT Settings* was not set, the data channel stayed clear. If the FTPS server rejects `PROT P`, the connection fails with the message `There was an error while trying to set the PROT Setting to P (PRIVATE)`. To keep the 2.x behavior, set `protSetting="CLEAR"` on `ftps:ftps-explicit-mode`. When the data channel is clear, the connector logs `CLEAR PROT Setting selected, data will be sent in plain text through the data channel` once per configuration at WARN. In 2.1.3, this warning was logged only in FIPS mode.
* *Primary Node Only* (`primaryNodeOnly`) on the *On New or Updated File* source now defaults to `true`. In a cluster, including CloudHub 2.0, only the primary node polls the directory. To poll on every node as in 2.x, set `primaryNodeOnly="false"` on the source.

=== Connection Changes

* In *Ftps implicit mode*, if the server rejects `PROT P`, the connection now fails with the message `There was an error while trying to encrypt the data channel (PROT P)`. In 2.x, the connector logged a warning and continued with a clear data channel. *Ftps implicit mode* has no clear fallback.
* If the configured *Working Directory* (`workingDir`) does not exist, the connection now fails when it is established with `FTPS:FILE_DOESNT_EXIST`. If it is a file, the connection fails with `FTPS:FILE_IS_NOT_DIRECTORY`. Both are children of `FTPS:CONNECTIVITY`. If the path is a directory that the user cannot enter, the connection fails with `FTPS:CONNECTIVITY` and the message `Access denied to the configured workingDir`. *Test Connection* and connection validation report these failures, and reconnection strategies apply. In 2.x, an invalid working directory was ignored and later operations ran in the wrong directory.

=== Error Type Changes

* The new `FTPS:TLS_HANDSHAKE_FAILED` error type is raised when the TLS handshake with the FTPS server or with an HTTPS tunnel proxy fails, for example because the server certificate is not trusted, the host name does not match, the certificate is expired, or no protocol or cipher suite can be agreed. `FTPS:TLS_HANDSHAKE_FAILED` is a child of `FTPS:CONNECTIVITY`. In 2.x, TLS handshake failures raised `FTPS:INVALID_CREDENTIALS`. Error handlers that catch only `FTPS:INVALID_CREDENTIALS` no longer catch TLS failures. Catch `FTPS:TLS_HANDSHAKE_FAILED` or `FTPS:CONNECTIVITY` instead.
* The `FTPS:FILE_NOT_FOUND` error type is removed. The connector never raised it. An app with an error handler that references `FTPS:FILE_NOT_FOUND` fails to deploy. Use `FTPS:ILLEGAL_PATH` instead.
* When the FTPS server rejects a file action with reply code 450, 550, or 553, the connector now classifies the error by the reply text:
** A reply that indicates missing permission (for example, `Permission denied`, `Access denied`, `Not authorized`, or `Forbidden`) raises `FTPS:ACCESS_DENIED`.
** A reply that indicates a missing file (for example, `No such file`, `Not found`, or `Does not exist`) raises `FTPS:ILLEGAL_PATH`, the same error the connector raises when it detects a missing path itself.
** A reply the connector cannot classify keeps the same generic error as in 2.x.
+
`FTPS:ACCESS_DENIED` is not a child of `FTPS:CONNECTIVITY`. In 2.x, these server rejections surfaced as `MULE:UNKNOWN`. Error handlers that catch only `FTPS:CONNECTIVITY` or `MULE:UNKNOWN` no longer catch permission failures. Catch `FTPS:ACCESS_DENIED` instead. Handlers that catch `ANY` are not affected.
* When the server refuses to create a directory with reply code 450, 550, or 553 and a reply text that does not explain the cause, for example `550 Create directory operation failed.`, the connector raises `FTPS:ACCESS_DENIED` if the path is still missing. If a file already occupies that name, the connector raises `FTPS:ILLEGAL_PATH`. This applies to *Create Directory* and to operations with *Create Parent Directories* set to true.
* *Read* and *Write* raise `FTPS:FILE_LOCK` when *Lock* is true and the file is already locked. *Delete* raises `FTPS:FILE_LOCK` when the file is locked by another operation in the app, for example a *Read* that is still in progress. The message is `File '<path>' is locked by another process` or `Could not lock file '<path>' because it's already owned by another process`.
* If the *Directory* configured in the *On New or Updated File* source does not exist, or the connector cannot enter it, the source fails at startup with `FTPS:ILLEGAL_PATH` and the message `Path '<directory>' doesn't exist`. In 2.x this failure was a generic runtime error.

=== Proxy Changes

* *Proxy host* (`host`) is now required in `ftps:http-tunnel-proxy` and `ftps:https-tunnel-proxy`. In 2.x, it was optional with an empty default, and configurations that omit it now fail validation.
* *Proxy port* (`port`) defaults to `3128`.
* In Anypoint Studio and Anypoint Code Builder, the proxy settings are now in the *Proxy* tab of the connection configuration.

=== Listener Changes

* *Primary Node Only* now defaults to `true`, as described in <<changed-defaults>>.
* Watermark resolution is one minute, the same as in 2.x. When *Watermark Enabled* is true and the server does not return a modification timestamp for a file, the watermark is ignored for that file and a `WARN` message is logged.

=== TLS Session Reuse

* On Mule 4.13.0 and later, the connector can reuse the control-channel TLS session on data channels through the Java (JDK) security provider, so it does not need to register the Bouncy Castle security providers for the whole JVM. This mode is opt-in. For the conditions and how to enable it, see xref:ftps-studio-configuration.adoc#configure-java[Configure Java JDK for Session Reuse]. In every other case, the connector reuses TLS sessions through Bouncy Castle, as in 2.x.
* When an app is undeployed, the connector now removes the Bouncy Castle security providers that it registered. Providers registered by the runtime or by other apps are kept.
* In FIPS mode, the connector uses the runtime FIPS security providers and reuses TLS sessions through Bouncy Castle, as in 2.x.

=== File Attributes

* File attributes are now of type `com.mulesoft.connectors.ftps.api.ftp.FtpsFileAttributes`. DataWeave expressions that read attribute fields, such as `attributes.name`, `attributes.path`, `attributes.size`, and `attributes.timestamp`, work unchanged.
* File attributes that FTPS Connector 2.x serialized, for example into an object store, a VM queue, or a persistent queue, cannot be read by version 3.0. Process or clear that data before you upgrade.

=== FTP and FTPS Connectors in the Same App

FTPS Connector 3.0 can be used in the same app as FTP Connector 2.0.4 or 3.0. Using FTP Connector 3.x with FTPS Connector 2.x in the same app is not supported. If the app uses both connectors, upgrade both to 3.0 together.

== Limitations

Before you perform the upgrade, be aware of these known limitations:

* TLS 1.3 sessions cannot be reused on data channels with either security provider. FTPS servers that require session reuse, such as vsftpd with `require_ssl_reuse=YES` or ProFTPD, reject the data channel when TLS 1.3 is negotiated. Mule 4.10 and later enables TLS 1.2 and TLS 1.3 by default, so set *Enabled Protocols* to `TLSv1.2` in the TLS context when you connect to these servers.
* Servers that do not support Extended Master Secret, for example servers that use OpenSSL 1.0.2, reject session reuse with a `522` reply on both security providers.
* *Test Connection* and connection validation check only the control channel. Session reuse problems appear on the first file transfer or listing.
* Closing a file stream before it is fully read waits for the server to finish the transfer. That wait ends when the server replies or when the socket timeout expires, and the close can fail if the transfer does not complete.
* On the JDK session-reuse path the connector does not register Bouncy Castle, so a `bcfks` keystore works only when Bouncy Castle is already registered by something else. Use a `jks` or `pkcs12` keystore on that path.
* The JDK discards TLS 1.2 session tickets that live longer than 7 days. vsftpd issues tickets with that maximum lifetime, so a data channel that depends on those tickets cannot resume and vsftpd returns `522`. Set `jdk.tls.client.enableSessionTicketExtension` to `false` before you use the JDK provider. For how to set it, see xref:ftps-studio-configuration.adoc#configure-java[Configure Java JDK for Session Reuse].

== Upgrade Prerequisites

Before you perform the upgrade, complete these tasks:

* Create a backup of your files, data, and configuration in case you need to restore to the previous version.
* Process or clear any FTPS Connector 2.x file attributes stored in object stores, VM queues, or persistent queues.

== Upgrade Steps

Follow these steps to perform the upgrade:

. In Anypoint Studio, create a Mule project.
. In *Mule Palette*, click *Search in Exchange*.
. In *Add Dependencies to Project*, enter `ftps` in the search field.
. In *Available modules*, select *FTPS Connector - Mule 4* and click *Add*.
. Click *Finish*.
. Verify that the `mule-ftps-connector` dependency version is 3.0 in the `pom.xml` file in the Mule project.
. If the app also uses FTP Connector, upgrade it to version 3.0.

Studio upgrades the connector automatically.

== Post-Upgrade Steps

After you install the latest version of the connector, update your app:

. Rename `connectionTimeoutUnit`, `responseTimeoutUnit`, and `timeBetweenSizeCheckUnit` to `connectionTimeoutTimeUnit`, `responseTimeoutTimeUnit`, and `timeBetweenSizeCheckTimeUnit`.
. On each `ftps:matcher`, replace `timeUnit` with `notUpdatedInTheLastTimeUnit`, `updatedInTheLastTimeUnit`, or both.
. If the connector configuration sets *Time Between Size Check* without a unit, set `timeBetweenSizeCheckTimeUnit="MILLISECONDS"` to keep the 2.x timing.
. If the FTPS server does not accept `PROT P` in explicit mode, set `protSetting="CLEAR"`. In implicit mode, fix the server configuration, because the connection fails.
. Replace error handlers for `FTPS:FILE_NOT_FOUND` with `FTPS:ILLEGAL_PATH`.
. Replace error handlers that catch only `FTPS:INVALID_CREDENTIALS` for TLS failures with handlers for `FTPS:TLS_HANDSHAKE_FAILED` or `FTPS:CONNECTIVITY`.
. Replace error handlers that catch only `FTPS:CONNECTIVITY` or `MULE:UNKNOWN` for permission failures with handlers for `FTPS:ACCESS_DENIED`. For the error types the connector raises, see xref:ftps-troubleshooting.adoc#common-throws[Understand Common Throws].
. Set *Proxy host* in every HTTP or HTTPS tunnel proxy configuration.
. Verify that the *Working Directory* of every connection exists on the server and is a directory the user can enter.
. In a cluster, including CloudHub 2.0, set `primaryNodeOnly="false"` on each *On New or Updated File* source that must poll on every node.
. If the app uses `ftp:*` operations or configurations, add FTP Connector to the app and replace any `ftps:connection` inside `ftp:config` with `ftps:config`.
. Update custom Java code that references `com.mulesoft.extension.ftps.*` classes to use `com.mulesoft.connectors.ftps.api.*`.

== Verify the Upgrade

After you install the latest version of the connector, follow these steps to verify the upgrade:

. In Studio, verify that there are no errors in the *Problems* or *Console* views.
. Verify that there are no problems in the project `pom.xml` file.
. Test the connection, and then run a file transfer or listing to verify that TLS session reuse on the data channel works. *Test Connection* checks only the control channel.

== Revert the Upgrade

If it is necessary to revert to the previous version of FTPS Connector, change the `mule-ftps-connector` dependency version in the project's `pom.xml` file to the previous version, for example 2.1.3, and restore the original XML, including the 2.x parameter names. If the app uses FTP Connector 3.0, revert it to 2.x as well.

You must update the project's `pom.xml` file in Anypoint Studio.
